# Hermes Android native/Desktop gap refresh — 2026-08-07

## Bottom line

The Android app is already a substantial remote Hermes client: the current
`dev` checkout has chat/session controls, streaming, approvals, profiles,
skills, cron, providers, MCP catalog management, files, voice, usage, billing,
diagnostics, and Command Center surfaces. The remaining work is not another
basic chat transport. To feel like a finished native client and to approach
the shipped Desktop feature set, the work should be ordered as follows:

1. Finish app-level Dashboard authentication (native OAuth/OIDC and a usable
   multiple-password-provider choice).
2. Add Android lifecycle delivery: background completion notifications,
   notification actions/deep links, and reliable resume after process death.
3. Close the rich conversation gap: exact reconnect/replay, generated
   artifacts, inline media, richer tool/citation rendering, and queued
   attachments.
4. Complete the remote management surfaces Desktop already exposes: MCP
   custom/OAuth configuration, toolset setup, profile identity/export, webhooks,
   pairing, automation blueprints, memory/curator, and maintenance export.
5. Finish Android-native quality: biometrics, shortcuts/widgets/app links,
   TalkBack/switch access, keyboard/foldable/multi-window QA, and a supported
   update/provenance story.

This comparison uses only the current Hermes Desktop/Agent source and this
repository. It does not use upstream Android proposals, issues, or pull
requests.

## Platform adaptations that should not be treated as accidental gaps

Some Desktop features are Electron/host capabilities rather than remote Hermes
product APIs:

- Desktop can run a local Hermes child process, connect through SSH, manage
  local/cloud/remote modes, and maintain Git worktrees. The connection modes
  and SSH controls live in [`gateway-settings.tsx`](https://github.com/NousResearch/hermes-agent/blob/eaa53de4eb00ac2686438f4d5e4c674158059ba9/apps/desktop/src/app/settings/gateway-settings.tsx#L34-L45)
  and the Electron lifecycle in [`main.ts`](https://github.com/NousResearch/hermes-agent/blob/eaa53de4eb00ac2686438f4d5e4c674158059ba9/apps/desktop/electron/main.ts#L7000-L7350). Android currently has a secured remote Dashboard URL flow in [`ManagementScreens.kt`](../../app/src/main/java/com/nousresearch/hermes/ui/ManagementScreens.kt#L68-L230).
- Desktop plugins/contributed routes, local filesystem reveal, terminal panes,
  Computer Use permission grants, global shortcuts, and update/uninstall are
  host-integrated. Android should not pretend to support them through a
  remote URL. Either document them as Android-adapted/host-managed, or define
  a separately consented Termux/companion contract; do not import an upstream
  Android implementation into this repository.
- Desktop’s pane tree, tabs, drag/drop, and large-screen keyboard workflow
  should become Android master/detail, drag/drop/share, and back-stack flows.
  The Android destination set already follows that adaptation rather than
  trying to copy Electron panes: [`HermesApp.kt`](../../app/src/main/java/com/nousresearch/hermes/ui/HermesApp.kt#L197-L199).

## Release/provenance issue found during the audit

The Android build embeds `AUDITED_HERMES_COMMIT` as the older
`5122ddd478143a6901bb752cf8ebcd1c5154b6da` in
[`app/build.gradle.kts`](../../app/build.gradle.kts#L55-L61), while this report
audits current Agent `eaa53de4...` and the previous auth refresh report used
`f15a38ee...`. This does not change runtime parity, but it makes diagnostics and
compatibility claims stale. Before release, make the build provenance a single
generated/pinned value and update the capability display and fixture metadata
to the exact tested upstream commit/version.

## Suggested execution order and definition of done

1. **Auth + lifecycle:** native app login, provider selector, encrypted token
   rotation, notification registration/revocation, action deep links, and
   process-death restoration.
2. **Conversation fidelity:** event replay/receipts, stable message identity,
   artifact/media extraction, rich tool/reference rendering, large upload
   progress, and queued attachment descriptors.
3. **Remote management:** MCP custom/OAuth/filtering, toolset setup, profile
   SOUL/import/export, webhooks/pairing, blueprint delivery, memory/curator,
   and maintenance export.
4. **Native polish:** biometrics, shortcuts/widgets/app links, transcript
   export/pinned sessions, TalkBack/switch access, keyboard/foldable/multi-
   window QA, and refreshed provenance/update UX.

The app should only be called fully featured after each item has a real
Android UI path, a typed request/response contract test, and physical-device
runtime proof where Android lifecycle or UI behavior is involved. Green unit
tests alone cannot prove background delivery, process death, browser auth,
notification actions, or foldable/accessibility behavior.
